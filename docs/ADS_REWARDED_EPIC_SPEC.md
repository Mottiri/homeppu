# 広告導入 + Epicリワード解放 仕様書

## 目的
- バナー広告で基礎収益を確保する
- Epicリアクションの「広告視聴による一時解放」で収益機会を増やし、サブスクの価値は維持する

## 対象スコープ
- Android/iOS（まずテストIDで実装）
- バナー広告は「TL / タスク / 投稿作成」画面の**上部**に表示
- Epicスタンプは**広告視聴で一時解放（1種類のみ）**

## 非対象
- サークル画面へのバナー表示
- 既存の徳ポイント（rare）解放ロジックの変更
- バナー以外の広告（インタースティシャル等）

---

## 仕様（確定）

### Epicスタンプ一時解放
- 一時解放は**1スタンプのみ**（視聴時に選択したスタンプ）
- 1回の視聴で**25回分**付与（`AppConstants.rewardedReactionUses`）
- **初回視聴から24時間固定**（`AppConstants.rewardedReactionHours`）。追加視聴で期限延長しない
- 期限切れ時は残回数があっても**リセット**
- 期限内は回数制限なし（視聴毎に25回追加可能）
- Epic残回数は**スタンプ右下の小バッジ**で表示（時間表示はしない）

### 残回数の同期方式
- スタンプバーを開いたタイミングで**サーバーと同期**（`Source.server` 指定で必ずサーバーから取得）
- 以降は**セッション内（ダイアログが開いている間）はクライアントで楽観UI管理**
- 押下時のサーバー失敗は**ロールバックしない**（次回バー表示時のサーバー同期で補正）

### バナー広告
- AppBar下に配置（TL / タスク / 投稿作成の3画面）
- サブスク加入時は非表示
- サークル系画面には非表示

### 投稿ごとのリアクション回数制限
- 1ユーザー1投稿あたり**最大5回**まで（`ReactionLimitService.maxReactionsPerPost`）
- 端末ローカル（SharedPreferences）に保存。保存キーは `reaction_count_{uid}_{postId}`
- スタンプバー表示前にサーバーの `reactions` を取得し、ローカル回数を補正
- ログアウト時に該当ユーザーのローカル回数を削除
- ユーザー単位でキー分離されており、別アカウントでログインしても回数は引き継がれない
- サーバー側でも同一制限をFirestoreの `reactions` コレクションで検証

## アーキテクチャ

### データモデル（Firestore）

`users/{uid}`:
```
rewardedReactionUnlocks: {
  [reactionType: string]: {   // 例: "rainbow", "hundred"
    remaining: number,         // 残回数
    expiresAt: Timestamp       // 有効期限
  }
}
```

`reactions/{reactionId}`:
```
postId: string
userId: string
userDisplayName: string
reactionType: string
createdAt: Timestamp
```

### Cloud Functions

#### 1. `grantRewardedReactionUnlock`（新規Callable）
- **認証必須 + AppCheck強制**
- 受け取り: `reactionType`
- Epicのみ許可（`EPIC_REACTIONS: Set = ["rainbow", "hundred"]`）
- **トランザクション内で処理**:
  - 既存有効期限が未来 → `remaining += 25` / `expiresAt` 維持
  - 期限切れ or 未設定 → `remaining = 25`, `expiresAt = now + 24h`

#### 2. `addUserReaction`（既存Callableの拡張）
- **認証必須 + AppCheck強制**
- **BANチェック**: トランザクション内でユーザードキュメントを取得し、`isBanned === true` または `banStatus != "none"` なら `permission-denied` を返す
- Epicリアクションは**サブスク or 一時解放**が必須
- 期限切れなら `rewardedReactionUnlocks.{reactionType}` を削除
- 通過時は `remaining` を `-1`（トランザクション内）
- 0以下になった場合は次回以降拒否

## 連続タップ対策: シリアルキュー + ペンディング追跡

### 経緯と課題

#### 問題1: Firestoreトランザクション競合
スタンプの連続タップ時、`unawaited(_sendReactionToServer())` でサーバー呼び出しが並列実行されていた。Firestoreトランザクションが競合し、一部の呼び出しが失敗して `remaining` がズレる問題が発生。

```
【修正前】
タップ1 → unawaited(サーバー呼び出しA)
タップ2 → unawaited(サーバー呼び出しB)  ← Aと並列で競合
タップ3 → unawaited(サーバー呼び出しC)  ← A,Bと並列で競合
→ Firestoreトランザクション競合、一部失敗、remaining のズレ
```

#### 解決: クライアント側シリアルキュー（`ReactionSyncService`）
サーバー呼び出しをキューに入れ、直列実行することで競合を防止。UIは即時反映を維持。
キューは**ユーザー単位でグローバル共有**し、投稿A/B間の並列送信を防ぐ。

```
【修正後】
タップ1 → UI即時反映 → キューにエンキュー → サーバー呼び出しA開始
タップ2 → UI即時反映 → キューにエンキュー → Aの完了を待機
タップ3 → UI即時反映 → キューにエンキュー → Bの完了を待機
  → A完了 → サーバー呼び出しB開始
  → B完了 → サーバー呼び出しC開始
  → C完了 → キュー空
```

**設計詳細**: [`docs/design/reaction_serial_queue_design.md`](design/reaction_serial_queue_design.md) を参照

#### 問題2: ダイアログ間のEpic残数ズレ
シリアルキュー導入後、投稿Aでスタンプを5回押した後、投稿Bのスタンプバーを開くと、キュー未処理分がサーバーに反映されていないため、サーバー同期で取得する残数が「まだ消費されていない」値になる。

#### 解決: `ReactionSyncService` のペンディング追跡
- サーバー未反映のEpicリアクション消費数を**ユーザー単位**で追跡
- キューにエンキュー時に `increment`、サーバー送信完了時に `decrement`
- スタンプバー表示時にサーバーから取得した残数からペンディング分を差し引いて表示

```
【ペンディング追跡のフロー】
投稿Aでスタンプ3回押す:
  → increment x3 → ペンディング: 3
  → サーバー呼び出し完了1つ → decrement → ペンディング: 2

投稿Bのスタンプバーを開く:
  → サーバーから remaining=22 を取得（1回分だけ反映済み）
  → ペンディング2を差し引き → 表示: 20（正確な値）
```

#### 問題3: 初回長押しでスタンプバーが表示されない
アプリ起動後の初回長押し時、ダイアログ表示前に以下のネットワーク呼び出しがあり、応答待ちで表示が遅延していた:
1. Firestore `.get()` によるBANチェック
2. `isAdminProvider.future` による管理者チェック（IDトークンのforceRefreshを含む）

#### 解決: キャッシュ済みプロバイダーからの即時取得
- BANチェック: `ref.read(currentUserProvider).valueOrNull` → Riverpod StreamProviderのキャッシュから即時取得
- 管理者チェック: `ref.read(isAdminProvider).valueOrNull ?? false` → 同様にキャッシュから即時取得
- サーバー側にもBANチェックを追加し、クライアント側キャッシュのラグを多層防御で補完

## セキュリティ評価

### 多層防御の構成

| レイヤー | 防御内容 | 実装箇所 |
|---------|---------|---------|
| **AppCheck** | 正規アプリからのリクエストのみ許可 | Cloud Functions `enforceAppCheck: true` |
| **認証** | ログイン済みユーザーのみ | Cloud Functions `requireAuth()` |
| **BANチェック（クライアント）** | BAN済みユーザーのUIブロック | `post_card.dart` キャッシュ済みプロバイダー |
| **BANチェック（サーバー）** | BAN済みユーザーのサーバー側拒否（`isBanned` または `banStatus != none`） | `addUserReaction` トランザクション内 |
| **Firestoreルール** | `rewardedReactionUnlocks` はクライアント直接変更禁止 | `firestore.rules` protectedFields |
| **トランザクション** | 残回数の競合防止 | `grantRewardedReactionUnlock`, `addUserReaction` |
| **サブスク/解放チェック** | Epicはサブスクまたは一時解放が必須 | `addUserReaction` トランザクション内 |
| **回数制限（サーバー）** | 1投稿5回まで | `addUserReaction` reactionsコレクション検証 |
| **回数制限（クライアント）** | 1投稿5回まで（即時UXフィードバック） | `ReactionLimitService` SharedPreferences |

### リスクと対策

| リスク | 影響度 | 対策 | 残留リスク |
|-------|--------|------|-----------|
| クライアントBANチェックのバイパス | 低 | サーバー側BANチェックで防御 | なし |
| BANチェックのキャッシュラグ | 極低 | StreamProviderのリアルタイム同期 + サーバー側二重チェック | BAN反映までの数秒間 |
| 不正な回数付与 | 中 | `grantRewardedReactionUnlock` はサーバー側トランザクションで付与。クライアントから直接Firestoreへの書き込みはルールで禁止 | なし |
| 残回数の不正消費回避 | 低 | `addUserReaction` でサーバー側トランザクション内で残数チェック・減算 | なし |
| 5回制限のすり抜け | 極低 | サーバー側でreactionsコレクションをカウント。ただしトランザクション外のため理論上は高速連打で1回余分に通る可能性あり | クライアント側制限で実質防御 |
| ペンディングの残留 | 極低 | ログアウト時にユーザー単位でクリア。アプリ再起動時にもリセット | 一時的な表示ズレ（数回分） |
| 広告視聴の不正スキップ | 低 | AdMob SDKの検証 + サーバー側で付与を制御 | AdMob SDK側の防御に依存 |

### セキュリティ上の判断

**クライアント側BANチェックのキャッシュ化について:**

当初はFirestoreへの直接 `.get()` で毎回サーバーに問い合わせていたが、以下の理由でキャッシュ済みプロバイダーに変更した:

1. **UX優先**: 毎回のネットワーク呼び出しにより、アプリ起動後の初回長押しでスタンプバーが表示されない致命的なUX問題があった
2. **実質的な安全性の維持**: `currentUserProvider` は Firestore `snapshots()` を使用した StreamProvider であり、リアルタイムに同期される。`.get()` による単発取得よりもむしろ更新頻度が高い
3. **多層防御の実現**: サーバー側 `addUserReaction` にもBANチェックを追加し、クライアント側のキャッシュラグを補完。仮にクライアント側チェックを完全にバイパスしても、サーバー側で拒否される

## 受け入れ基準
- [ ] サブスク未加入ユーザーはEpicスタンプがロック表示
- [ ] リワード視聴完了で**同一スタンプのみ**25回分付与
- [ ] 24時間経過で残数があっても無効化
- [ ] 期限内はスタンプがロック解除され使用可能
- [ ] 期限後は再び広告視聴で再解放
- [ ] バナーはTL/タスク/投稿作成に表示され、サブスク加入で非表示
- [ ] スタンプ連打時にUIが即時反映される
- [ ] スタンプ連打時にサーバーへの送信が直列化され、全て正しく記録される
- [ ] 異なる投稿間でスタンプバーを開き直しても、Epic残数が正確に表示される
- [ ] アプリ起動後の初回長押しでスタンプバーが即座に表示される
- [ ] BANユーザーはクライアント・サーバー両方でリアクションがブロックされる

## テスト観点（手動）
1. 非課金ユーザーでEpicスタンプをタップ → ダイアログ表示
2. リワード視聴 → 25回分付与 → 使用可能
3. 24時間経過後 → ロックに戻る
4. バナーがTL/タスク/投稿作成に表示される
5. サブスク加入時はバナー非表示
6. スタンプを素早く5回連打 → UIは即座に5回反映、サーバーにも5回記録
7. 投稿Aで3回押した後、投稿Bのスタンプバーを開く → Epic残数が正確
8. アプリ起動直後に投稿を長押し → スタンプバーが即座に表示
9. BANユーザーでリアクション試行 → クライアント側でブロック
10. 旧投稿を長押し → サーバー同期で回数補正が入り、上限判定が正しく動作
11. 長押し時のサーバー同期が体感速度に影響しないことを確認
