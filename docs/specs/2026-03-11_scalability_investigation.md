## 調査概要

Flutter + Firebase SNSアプリ「ほめっぷ」のコードベースを全面的に読み解き、ユーザー規模拡大時のスケーラビリティリスクを洗い出した。Claude Code が一次調査を行い、Codex がリポジトリを独立に読んで検証・追加指摘を行った。

## リスク一覧（深刻度順）

### P0: 最重要（1,000人規模で顕在化）

#### 1. フォロー関係の配列モデル

**深刻度**: Critical
**顕在化規模**: DAU 1,000人〜
**コンポーネント**: `users/{uid}` ドキュメント

**現状**:
- `users.following[]` / `users.followers[]` にユーザーIDを配列で保存
- フォロー/アンフォロー時にトランザクションでドキュメント全体を読み書き
- フォロー中フィードは配列を10件ずつチャンクして `whereIn` 並列クエリ

**問題**:
- Firestoreドキュメントサイズ上限1MB → フォロワー数万人で上限到達
- フォロー操作のたびにユーザードキュメント全体の読み書き → 書き込み競合
- フォロー100人で10並列クエリ、1000人で100並列クエリ → 読み取りコスト爆発
- `currentUserProvider` がユーザードキュメントをwatchしており、配列変更で画面全体がリビルド

**対策案**:
- `users/{uid}/following/{followeeId}` サブコレクション化
- フォローフィードをサーバー側 Fan-out-on-Write に移行（性能改善設計書 #6 Phase 2）
- フォロー数は `followingCount` / `followerCount` フィールドで非正規化管理

**関連ファイル**:
- `functions/src/callable/users.ts`（フォロー/アンフォロー処理）
- `lib/features/home/presentation/screens/home_screen.dart`（フォローフィードクエリ）
- `lib/shared/models/user_model.dart`（配列フィールド定義）

#### 2. 投稿ドキュメントのホットスポット（Codex指摘）

**深刻度**: Critical
**顕在化規模**: DAU 1,000人〜（人気投稿発生時）
**コンポーネント**: `posts/{postId}` ドキュメント

**現状**:
- 人間コメント・AIコメント・人間リアクション・AIリアクションが同一投稿ドキュメントの `commentCount` / `reactions.*` を更新
- 1つの投稿に対して短時間に多数の書き込みが集中

**問題**:
- Firestoreの単一ドキュメント書き込み上限: 1回/秒
- 人気投稿にAIコメント5件 + AIリアクション10件 + 人間のリアクションが集中 → 競合エラー

**対策案**:
- 分散カウンタパターンの導入（シャード化）
- リアクション集計を非同期バッチ更新に変更
- `commentCount` をトリガーではなく定期集計に切り替え

**関連ファイル**:
- `functions/src/callable/comments.ts`（コメント作成時のカウント更新）
- `functions/src/callable/reactions.ts`（リアクション追加時のカウント更新）
- `functions/src/triggers/posts.ts`（AI生成タスクの投入）

---

#### 3. Cloud Functions の idempotency 不足（Codex指摘）

**深刻度**: High
**顕在化規模**: DAU 500人〜
**コンポーネント**: `onPostCreated` トリガー、通知トリガー

**現状**:
- 1投稿作成で AIコメント1-5件 + AIリアクション5-10件の Cloud Tasks を投入
- 下流でコメント作成 → 通知作成 → FCM送信が連鎖
- idempotency key なし、再試行で重複実行

**問題**:
- Cloud Functions のリトライで同じAIコメントが複数生成される
- 通知が二重送信される
- Cloud Tasks キュー `generateAIComment` に全種類のタスクが集約

**対策案**:
- deterministic な Task ID（`postId + aiUserId + type` のハッシュ）で重複防止
- 通知作成に idempotency ドキュメントを使用
- Cloud Tasks キューをタスク種別ごとに分離

**関連ファイル**:
- `functions/src/triggers/posts.ts`（AI生成タスク投入）
- `functions/src/triggers/notifications.ts`（通知トリガー）
- `functions/src/helpers/notification.ts`（FCM送信）

### P1: 重要（5,000人規模で顕在化）

#### 4. サークル一覧・検索のクライアント全件処理

**深刻度**: High
**顕在化規模**: DAU 5,000人〜（サークル数百件以上）

**現状**:
- `circles` コレクション全件をクライアントで取得・フィルタ・ソート
- 部分一致検索もクライアント側で実施
- `memberIds` 配列をサークルドキュメントに直接保持

**対策案**:
- サーバー側クエリに移行（Firestoreインデックス活用）
- 全文検索は Algolia / Typesense 等の外部サービス検討
- `memberIds` をサブコレクション化

**関連ファイル**:
- `lib/shared/services/circle_service.dart`

#### 5. コメントの無制限リアルタイムストリーム（Codex指摘）

**深刻度**: Medium-High
**顕在化規模**: DAU 5,000人〜（コメント100件超の投稿発生時）

**現状**:
- `comments.where(postId==...).orderBy(createdAt).snapshots()` でページネーションなし
- クライアント側で表示フィルタリング

**対策案**:
- コメントストリームに `limit()` を追加しページネーション化
- 初期表示は最新20件、スクロールで追加読み込み

**関連ファイル**:
- `lib/features/post/presentation/screens/post_detail_screen.dart`

---

#### 6. 通知の未読カウント・一括既読処理

**深刻度**: Medium
**顕在化規模**: DAU 5,000人〜

**現状**:
- 未読数を live query で毎回カウント
- `markAllAsRead` は未読ドキュメント全件を取得してバッチ更新

**対策案**:
- 未読数を `users/{uid}` の `unreadNotificationCount` フィールドで非正規化
- 通知作成時にインクリメント、既読時にリセット

**関連ファイル**:
- `lib/shared/repositories/notification_repository.dart`

### P2: 要注意（10,000人規模で顕在化）

#### 7. Firestoreセキュリティルールの多段get()

**深刻度**: Medium
**顕在化規模**: DAU 10,000人〜

**現状**:
- コメント/リアクション削除時に `posts` → `circles` → オーナーの3段階 `get()`
- Storage ルールでもサークルメディア書き込みごとにFirestore参照

**対策案**:
- 権限情報の非正規化（コメントに投稿者ID/サークルオーナーIDを埋め込み）
- 削除権限チェックをCloud Functions側に移動

---

#### 8. AI APIのコスト・レート制限

**深刻度**: Medium
**顕在化規模**: DAU 10,000人〜

**現状**:
- 1投稿あたり: モデレーション1回 + AIコメント1-5回 + AIリアクション5-10回
- Gemini 2.5 Flash: 無料枠 15 RPM / 1,500 RPD
- OpenAI gpt-5-mini: 従量課金

**対策案**:
- AI生成頻度の動的調整（ユーザー数に応じてAI応答確率を下げる）
- 短文（10文字未満）のモデレーションスキップ
- レスポンスキャッシュ

---

#### 9. クリーンアップジョブのコレクション走査

**深刻度**: Low-Medium
**顕在化規模**: DAU 10,000人〜

**現状**:
- 深夜に7個のスケジュールジョブが集中実行
- 一部のジョブはコレクション全件走査

**対策案**:
- ジョブの時間分散
- 削除対象フラグ + インデックスによる絞り込みクエリ
- BAN クリーンアップ用の複合インデックス追加

## コスト概算

以下は DAU（1日のアクティブユーザー数）を基準とした月額概算。
前提: 1ユーザーあたり1日平均 投稿0.5件、コメント2件、リアクション5件、フィード閲覧10回。

| 規模 | Firestore | Cloud Functions | Storage | AI API | **合計** |
|------|-----------|-----------------|---------|--------|---------|
| **100 DAU** | 無料枠内 | 無料枠内 | 無料枠内 | 無料枠内 | **$0** |
| **1,000 DAU** | ~$5-15 | ~$5-10 | ~$1-3 | ~$10-30 | **~$20-60** |
| **10,000 DAU** | ~$50-150 | ~$50-100 | ~$10-30 | ~$100-300 | **~$200-600** |
| **100,000 DAU** | ~$500-2,000 | ~$500-1,500 | ~$100-300 | ~$1,000-5,000 | **~$2,000-9,000** |

**注意**:
- 100,000 DAU の Firestore コストはフォロー配列モデルのままだと読み取り fan-out で **$5,000-10,000+** に膨らむ可能性大
- AI APIコストは投稿あたりの生成数を現状（最大15回/投稿）で試算。動的調整すれば大幅削減可能
- Storage はCDNキャッシュの効き方で変動
- 上記は Blaze プラン（従量課金）前提

**Codex総合判定**: 「小規模〜中規模なら成立。ユーザー増で最初に Firestore 読取 fan-out と投稿周辺の書き込み集中が崩れる」

## 調査の信頼性

- **Claude Code調査**: コードベースを直接読んだ事実ベースの分析。Firestoreクエリパターン、Cloud Functions構成、AI呼び出しパターン、リアルタイムリスナー箇所を網羅的に洗い出し
- **Codex検証**: リポジトリを独立に読み、Claude Codeの調査を検証。追加で3つの重要指摘（ホットドキュメント、idempotency不足、コメント無制限ストリーム）を発見
- **コスト概算**: Firebase公式料金体系に基づく推定値。実際のコストはユーザー行動パターンに大きく依存するため、あくまで目安

**リスクと対策**: 本調査はコード読解に基づく静的分析。実際の負荷テスト（Firebase Emulator + 負荷ツール）は未実施。本番環境でのモニタリング（Firebase Usage Dashboard）を併用することを推奨。
